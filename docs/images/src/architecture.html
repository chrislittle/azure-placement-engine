Azure Quota Vending: how it fits together

A subscription vending module creates a subscription. It arrives with Azure's default quota, which is often zero for the family the workload needs. AQV runs next, as a second stage, and takes one value from the first: the subscription ID. It deploys nothing. It sets quota and names the family and the sizes the application team should deploy into.

Where the quota comes from the pool is not built yet
Quota group to build
Microsoft.Quota/groupQuotas, held at a management group. A pool the platform fills by reclaiming quota that subscriptions hold and never use. Allocating out of it is self-service and succeeds.

This is the design. Until it is built, available is null on every family, nothing is allocatable, and an ask above the current limit comes back infeasible.
Why not just ask Azure for more
A per-subscription quota increase is evaluated, not granted. It is refused when regional capacity is short, and the refusal arrives minutes later with a code that cannot be retried.

A vending pipeline cannot depend on that, so AQV does not ask. A family is only chosen when the quota it already holds, or a pool behind it, covers the request.

Bicep only writes
existing needs a known resource ID and fails the whole deployment when the resource is absent. deploymentScripts is idempotent, so a quota read would keep its first value. AQV has to report a missing region grant as an answer, not as a crash, so on that path PowerShell reads and decides and Bicep writes.
What stops them drifting
The decision logic exists twice, so conformance/ holds one set of language-neutral scenarios that both implementations must pass. It has already caught four real divergences, including one where Terraform returned an empty size list while PowerShell did not.
