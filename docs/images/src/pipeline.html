Running it in GitHub Actions

Three workflows ship in .github/workflows. One needs no Azure at all and runs on every push. The other two are stage 2, one per path, and neither writes anything unless it is asked to.

The workflows
WorkflowTriggerWhat it does
conformance.yml push, pull request Runs both implementations against the shared scenarios, plus terraform test. No Azure needed.
vend-stage-2-terraform.yml workflow_dispatch, or called Stage 2, Terraform path. Plans by default; writes only when asked.
vend-stage-2-bicep.yml workflow_dispatch, or called Stage 2, Bicep path. PowerShell reads and decides, Bicep writes.
Wiring stage 2 to stage 1 one value crosses
stage-1-vending
Creates the subscription and puts its ID in $GITHUB_OUTPUT.
needs: stage-1-vending
stage-2-quota
Takes subscription_id, the request file and apply_writes. Everything else it needs is in the repository.
In one pipeline
stage-2-quota:
  needs: stage-1-vending
  uses: ./.github/workflows/vend-stage-2-terraform.yml
  with:
    subscription_id: ${{ needs.stage-1-vending.outputs.subscription_id }}
    request_file: requests/payments-api.yaml
    apply_writes: true
subscription_id is the entire handoff contract, and avm-ptn-sub-vending already outputs it. The vending module needs no changes.
Identity and rights no stored secrets
OIDC federated credential
permissions: id-token: write, with AZURE_CLIENT_ID and AZURE_TENANT_ID as repository variables. Nothing is stored. The subject must match what the workflow presents, or the login fails without saying why.
▶assumes
Two roles, on the vended subscription
Reader for Microsoft.Compute/skus, locations/usages and provider registration.
Quota Request Operator for Microsoft.Quota/quotas/write, and Microsoft.Support/* with it.

Contributor also works and grants far more than AQV needs.
Reviewing before writing the reason for two stages
The plan is meaningful
Stage 2 runs against a subscription that already exists, so the plan shows the chosen family, the quota to write and why every other family was rejected. One module would have to defer every read until apply, and the decision would never appear in a plan at all.
apply_writes defaults to false
A run with it off evaluates the whole decision and writes nothing. That is the normal way to look at an answer, and it needs only Reader.
A refusal fails the run
On purpose. Terraform cannot catch a resource error, and a vended subscription that cannot run its workload is a failure rather than a caveat. Read the quota back afterwards: a write can succeed in Azure and still fail the apply.
Runners GitHub-hosted unless you say otherwise
VariableUnsetSet
CI_RUNNER_LINUX ubuntu-latest That label. Terraform and Bicep jobs. Needs az.
CI_RUNNER_WINDOWS ubuntu-latest That label. PowerShell jobs. Needs pwsh.
Do not set a runner variable before the runner is registered and online, or jobs queue waiting for a runner that does not exist. Self-hosted runners cannot be shared between repositories on a personal account — runner groups, the mechanism for sharing, exist only for organizations. A public repository gets unlimited GitHub-hosted minutes for standard runners, and then none of this is needed.
