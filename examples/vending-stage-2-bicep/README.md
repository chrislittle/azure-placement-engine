# Stage 2, the Bicep way

The same stage-2 job as [`../vending-stage-2`](../vending-stage-2), for shops
that run Bicep rather than Terraform.

```bash
pwsh -File Invoke-AqvVending.ps1 -SubscriptionId <from stage 1>
pwsh -File Invoke-AqvVending.ps1 -SubscriptionId <from stage 1> -Deploy
```

Writes are off by default, so the decision can be reviewed before anything is
written. It reads the **same request file** as the Terraform path.

## Why this is a script and a template, not a module

Bicep cannot read quota state — see
[decision 0001](../../docs/GUIDE.md#why-bicep-works-differently).
`existing` fails the whole deployment with `NotFound` when a resource is absent.
`deploymentScripts` is idempotent, so a quota read would keep its first value.

So the shape is:

```
PowerShell:  read quota + SKUs  ->  decide  ->  aqv-apply.bicepparam
Bicep:       aqv-apply.bicep    ->  write the quota

             quota group (the pool)  ->  allocate     NOT BUILT YET
```

On the Terraform path all three steps are Terraform. Here only the last one can
be Bicep.

The script makes no decision of its own. It serialises `writes_required`
unchanged, so the Bicep template receives what the Terraform module would
apply.

## A real run

Asking for 8 vCPUs of `GeneralPurpose` in `eastus`, against a PayAsYouGo
subscription that already holds 10:

```text
Reading eastus for 20c6f426-be9e-48a9-84d7-1f0e6395eef9 ...

  status   : satisfied
  reason   : existing quota covers the request
  category : GeneralPurpose
  family   : StandardDadsv7Family
  writes   : 0

Wrote C:\Users\Chris\azure_placement_engine\examples\vending-stage-2-bicep\aqv-apply.bicepparam
Re-run with -Deploy to apply it.
```

`satisfied` with no writes means the quota is already there, so the generated
parameter file has nothing in it:

```bicep
// GENERATED by Invoke-AqvVending.ps1 -- do not edit.
// Decision: satisfied -- existing quota covers the request
using '../../bicep/aqv-apply.bicep'

param region = 'eastus'
param writesRequired = [

]
```

When a write is needed, each entry carries the scope, the name and the absolute
new limit, which is the shape
[`bicep/aqv-apply.bicep`](../../bicep/aqv-apply.bicep) takes. The file is
regenerated on every run and is not committed.

The shipped sample request asks for 64 memory-optimized vCPUs, which the same
subscription cannot reach:

```text
  status   : infeasible
  reason   : no candidate family can reach 64 vCPUs
  category : MemoryOptimized
  family   :
  writes   : 0

Wrote C:\Users\Chris\azure_placement_engine\examples\vending-stage-2-bicep\aqv-apply.bicepparam
Nothing to deploy: the decision did not produce a workable placement.
```

The script exits 1 there, so a pipeline stops.

## Business rules

`-RulesFile` takes the same `rules.yaml` the Terraform path takes through
`-var rules_file`, so both paths apply the same rules. It defaults to
[`../vending-stage-2/rules.example.yaml`](../vending-stage-2/rules.example.yaml).

```powershell
./Invoke-AqvVending.ps1 -SubscriptionId $sub `
    -RequestFile ../../requests/my-app.yaml `
    -RulesFile ../../platform/rules.yaml
```

## Drift

The decision logic exists twice. [`conformance/`](../../conformance) holds one
set of scenarios. Both implementations must pass all of them. Run it in CI.
